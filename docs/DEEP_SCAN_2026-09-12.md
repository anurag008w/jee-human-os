Scope: complete read of `src/**` (51,054 lines of app code + 109 test files), `public/**`,
`index.html`, `vite/tsconfig/capacitor/oxlint` configs, `scripts/**`, `.github/workflows/**`,
and `android/**` (Java + manifest + gradle).

## 1. S1 — Data-loss and state-corruption bugs

### 1.1 Memory store load/save keeps the OLDEST 200 entries — newest memories are dropped ✅verified
`normalizeMemoryStore()` truncates with a head slice:

- `src/core/domain/memory.ts:137` → `entries: entries.slice(0, MEMORY_MAX_ENTRIES)`
- summaries likewise `:138`.

Entries are **appended newest-last** (`src/features/ai/memory.service.ts:71`), so `slice(0, 200)`
keeps the oldest 200 and throws away everything newer. This normalizer is not a one-off path — it
runs on **every load AND every save** (`LocalStateRepository.load` `state-repository.ts:145`,
`save` `:157`), and on every sync merge and backup import (both funnel through `normalizeState`).

Reachable triggers:
- `mergeAppState` unions memory entries from two devices with no cap (`src/features/sync/sync-merge.ts:81-95`) → merged store > 200 → on the next save the newest half of the merged memory is silently discarded.
- backup import / `importMemory` (`memory.service.ts:289`) of a bigger file — same drop.
- any store that ever exceeded 200 entries (e.g. long chat-archive writes from `chat.service`).

`MemoryService.prune()` caps at 200, but it is only called from `add()`; writes that bypass `add()`
(chat transcript archives, restore paths) grow the store past the cap.

**Fix:** keep the tail, not the head — sort by `createdAt` desc (or `slice(-MAX)`) before capping,
and cap after merge. Add a regression test with 260 entries asserting the newest survives.

### 1.2 Chat restore/import trims the wrong end — the newest messages of every session are lost ✅verified
- `src/features/chat/chat.service.ts:235` (`replaceStore`): `s.messages.slice(0, MAX_MESSAGES_PER_SESSION)`
- `src/features/backup/backup.service.ts:166` (`normalizeChatSessions`): same head slice.

Everywhere else the app drops the **oldest** on overflow — `chat.service.ts:320-321`, `:349-350`,
`:1770-1771` all use `session.messages.splice(0, overflow)`. Messages are stored chronologically
(`push` in `appendMessage`).

`replaceStore` is the entry point for: backup import, `delete-all` rollback, account isolation, and
**sync restore** (`sync-coordinator.ts` → `replaceStore(mergeChatSessions(...))`).
`mergeChatSessions` unions both devices' messages, so a 2-device user routinely lands >100 messages
per session — the restore then keeps the 100 oldest and silently deletes the most recent conversation.

**Fix:** `slice(-MAX_MESSAGES_PER_SESSION)` in both places (and cap sessions by `updatedAt` desc).

### 1.3 `restDays` can receive a duplicate day number → whole journey calendar shifts
`setDayMode` appends without a membership check:

- `src/features/chat/chat-tools.service.ts:1969-1970`
  `nextRest = wantsRest ? [...restDays, d] : ...` — if the day is simultaneously in `restDays`
  and `testDays`, the early "already X" guard (`:1965`) fails and `d` is appended **again**.
- Nothing dedupes it on the way back in either: `state-repository.ts:84` (`Array.isArray(r.restDays) ? r.restDays : []`).

`restDays` is the input to `restRawPositions()` (`src/features/habit-engine/dates.ts:50-53`), which
assumes sorted **unique** values: `[5,5]` produces raw rest slots `[5,6]` → every content day from 5
onward shifts by an extra calendar day. Symptom: plans/completion logs/mastery land on wrong dates
for the rest of the journey, and `contentDayForDate` disagrees with `dateForContentDay`.

How a day gets into both lists: `mergeAppState` unions `restDays` and `testDays` **independently**
with no exclusivity rule (`src/features/sync/sync-merge.ts:104-111`) — device A marks day 5 rest,
device B marks day 5 test → merged state has both. That is already a bug by itself (a "rest day"
that also schedules mock-test tasks), and it arms the duplicate-append above.

**Fix:** `Array.from(new Set(...))` + sort in `normalizeState`, dedupe in `mergeAppState`, and
enforce rest/test exclusivity in `setDayMode` + merge (rest wins or explicit conflict resolution).

### 1.4 AI action history stores whole-collection snapshots, 90 days, no count cap → localStorage quota → the app stops persisting
- `src/core/domain/ai-actions.ts:235` pushes `{ beforeState, afterState }` per action; `markDone`
  passes the **entire `state.taskLogs`** map (`chat-tools.service.ts:2054-2055`), `addTask`/`editTask`
  pass the entire `dynamicTaskBank` (`:2013-2014`).
- Retention is time-only: `AI_ACTION_HISTORY_RETENTION_DAYS = 90` (`ai-actions.ts:51`) with
  `pruneVersions` filtering by timestamp (`:313-315`) — **no max-version cap**.

The only size safeguard on save prunes **memory**, nothing else
(`state-repository.ts:148-156`); once `aiActionHistory` alone crosses `STATE_SAVE_BUDGET`, the
trimmed re-serialize is still too big, `PersistentStorage.set` hits quota, and *every* subsequent
save fails — progress stops persisting app-wide while the UI keeps working from cache (so the loss
is only discovered after a restart). This is the same failure class the audit fixed for memory (M7)
but the vector remains open for history/snapshots.

**Fix:** store a per-entity patch (`{logKey, taskId, prev}`) instead of whole collections, cap
`versions` at ~50 with a byte budget, and make the save-time safeguard fall back to dropping
history before failing the whole write.

### 1.5 Undo of an AI `markDone` reverts *every* day's completion log
`markDone`/`bulkMarkDone` snapshot `beforeState: state.taskLogs` (whole map, all days) —
`chat-tools.service.ts:2050-2059`, `:2098-2104` — and `restoreVersionBefore()` applies that snapshot
verbatim (`ai-actions.ts:253-266`). UI toggles (`TodayScreen.tsx:827-831`) do **not** create versions,
so "Undo" in Chat (`ChatScreen.tsx:3410`) silently wipes every manual completion recorded after the
AI action, across the whole journey.

**Fix:** delta-based undo (restore only the touched `logKey`/`taskId`), or refuse undo when a newer
non-versioned mutation is detected.

### 1.6 Registry declares `entityType`s that `applySnapshot()` cannot apply; those actions bypass the audit trail entirely
`applySnapshot` handles `dynamicTaskBank | taskLogs | restDays | testDays | dayModes | aiSettings`
(`ai-actions.ts:280-306`) and **returns the state unchanged for anything else**. The registry declares:

- `entityType: 'taskBank'` → `editAnyTask`, `deleteAnyTask` (`chat-tools.service.ts:135-136`)
- `entityType: 'customBlocks'` → `createBlock`, `deleteBlock`, `activateBlock` (`:138-140`)

Both groups sidestep `executeAiAction` and call `this.store.save()` directly (`:1633`, `:1668`,
`:1388`, `:1420`, `:1434`, `:1482`, `:1509`). Consequences:
1. no version is recorded → the "versioned, undoable audit trail for AI-generated changes"
   (`state.ts:266`) is a lie for task-bank and block edits — a deleted task/block is unrecoverable
   from AI Activity;
2. if anyone routes them through `executeAiAction` later, the mutation is silently discarded
   (apply no-op) while the tool reports `ok: true`;
3. `createBlock` force-sets `journeyComplete: true` + `completedAt` (`:1391-1392`) — creating a block
   on Day 6 flips the user into post-journey mode.

**Fix:** add `'taskBank' | 'customBlocks' | 'customTodos'` branches to `applySnapshot` (or use a
generic `{field, patch}` snapshot), route block/bank writes through `executeAiAction`, and stop
mutating `journeyComplete` as a side effect of block creation.

### 1.7 `resetAll` half-resets the app and pushes the empty state to the cloud backup
`useAppState.resetAll` (`src/lib/useAppState.ts:110-115`) → `update(() => emptyAppState())` only.
But `store.save` marks the `state` scope dirty (`container.ts` `store.save` → `syncCoordinator.markDirty`),
so a **reset silently overwrites the server backup** (last-write-wins, `sync.service.ts` header), while
chat, `misa` scope (relationship memory, scheduled calls) and provider keys stay intact and are
**re-merged back in** on the next focus reconcile (`sync-coordinator.ts:reconcileIfStale`) — the user
sees their progress "come back" and their cloud backup destroyed. `delete-all` (`features/sync/delete-all.ts`)
is the correct, transactional path; `resetAll` is a second destructive path with different semantics
(reachable from `ReviewScreen` → `resetAll` prop).

**Fix:** make `resetAll` delegate to `deleteAllData`'s snapshot/flush/detach sequence, or remove it
and point users at Settings → Delete all data.

### 1.8 Daily-summary rollup can drop memory written while it ran
`src/lib/useAppState.ts:60-86` runs `runDailyPipeline(s, date)` off a snapshot `s`, then
`container.store.save(mergeDaySummary(latest, next, date))`. `mergeDaySummary`
(`src/features/ai/summary-scheduler.ts:29-37`) copies `memory: next.memory` — the **pre-run** memory.
The pipeline is AI-enriched (seconds to minutes), and every memory write in that window (chat
archiving, `addMemory` tool, pin/edit) is overwritten. The function's own comment claims only
"summary fields + the pipeline's memory additions" are taken — it actually replaces the store.

**Fix:** merge by id: `{...latest.memory, entries: [...latest.memory.entries, ...onlyNewPipelineEntries]}`.

### 1.9 `deleteAllData` rollback does not cover Misa's own blobs
`src/features/sync/delete-all.ts:78-84` destroys `relationshipManager.resetLocal()` and
`proactiveAgentService.resetLocal()` — but the snapshot/rollback (`:91-105`) restores only
chat + state + data-owner + sync session. If any later step throws (e.g. `configureServerAuth` /
`attach` / `flush`), the user gets "delete failed, your data is intact" while Misa's relationship
memory and all scheduled messages/calls are gone for good.

**Fix:** snapshot both blobs (they're plain JSON in `persistentStorage`) and restore them in `rollbackDelete`.

### 1.10 `PersistentKeyValueStore.reload()` clears the cache before repopulating (write race)
`src/infra/storage/local-storage.ts:26-38`: `this.cache.clear()` → `await persistentStorage.keys()`
→ `await …get(key)` per key. During those awaits, `getItem()` returns `null` for every key, and any
`setItem()` that lands in the window can be **overwritten by the stale disk value** the loop is still
reading. This runs at boot (`persistentStoreReady`) and on every `visibilitychange → visible`
(`container.ts` reload hook) — i.e. exactly when a background write may be completing.

**Fix:** build a fresh `Map`, then assign (`this.cache = next`) atomically; never clear-then-await.

### 1.11 Backup `tasks` scope exports fields it never restores (asymmetric import)
Export (`src/features/backup/backup.service.ts:230-238`) writes `customHabits` and `masteryPlacement`;
the scoped import (`:359-366`) restores only `dynamicTaskBank`, `customTodos`, `studyVault`, `taskLogs`,
`planCache`, `restDays`, `testDays`. A `tasks` backup/restore therefore loses all user/AI habits and
every manual mastery placement (which pins/schedules mastered tasks) — permanent.
Also: the header promises scoped imports "MERGE into the current store", but the implementation
**replaces** each carried key wholesale (`next.taskLogs = rawState.taskLogs`), so importing an older
`tasks` file deletes newer local logs.

**Fix:** restore the missing keys; either implement a real merge (reuse `mergeAppState`) or rename the
behaviour in the docs/UI so the replace is explicit.

### 1.12 Android: `MainActivity` static state cleared by the OLD activity on recreation
`android/app/src/main/java/com/anurag/levelup/MainActivity.java:155-163` —
`onDestroy()` unconditionally does `liveCallActive = false; instance = null;`. On configuration change /
PiP re-parent / split-screen, the old activity's `onDestroy` runs **after** the new activity's
`onCreate` (`instance = this` at `:145`), so the fresh activity ends up with `instance == null` and
`liveCallActive == false`: `enterPictureInPicture()` (`:63-76`) becomes a silent no-op and
`onUserLeaveHint` (`:118-123`) stops auto-PiP-ing **mid live call** — the exact failure the class
comment says it fixes. `livePlugin` (`:20`) is a static that is never cleared, so a destroyed plugin
instance keeps receiving `onPiPModeChanged` (`:136-139`) and notifies a dead bridge.

**Fix:** `if (instance == this) instance = null;`, same guard for `livePlugin`, and re-assert
`liveCallActive` from `LiveCompanionForegroundService.isActive()` in `onResume`.

### 1.13 Gapless audio: unbounded native queue + release/write race  
**FIXED 2026-09-12** (bounded drop-oldest queue, `sinkLock` + join-before-release, write retry, fade-in, 500ms buffer) — see `docs/live_voice_cut_rootcause.md`.
`android/.../GaplessAudioTrackPlugin.java`:
- `write()` only ever `pending.offer(samples)` (`:148-152`) on an unbounded `LinkedBlockingQueue`;
  a network stall (producer keeps pushing 24 kHz PCM) grows native memory without limit, and there
  is no back-pressure signal to JS.
- `closeTrackInternal()` (`:184-206`) calls `t.pause()/stop()/release()` with no synchronization
  against `drainLoop()` (`:216-240`) which may be blocked inside `t.write(...)` on the writer thread
  → `IllegalStateException` / dropped tail audio / native abort on some OEMs.
- `open()` failure path leaves `writerThread` from a previous session untouched when
  `AudioTrack.Builder()` throws before `closeTrackInternal()` completes… (minor, same guard fix).

**Fix:** bounded queue (`offer` with capacity + drop-oldest or reject to JS), and a lock/generation
token around `audioTrack` so release never overlaps write.

## 2. S2 — Wrong results the user (and the AI) act on

### 2.1 AI fallback task is created with a habit id that does not exist
`src/features/ai/task-generation.service.ts:139` → `habitId: input.habitId ?? 'h1'`. The habit bank
has 88 ids (`daily_planning`, `deep_work`, …) — **no `h1`** (verified against
`src/features/task-bank/seed/habits.json`). Every habit lookup for it returns undefined
(`task-bank.repository.ts:75-77`), so `habitFirstActiveDay` → `null` → habit streak/score always 0
(`habit-engine/habits.ts:52-56, 76-79`), and Levels/habit grouping can never place the task.
Every AI-generation failure path (LLM off-schema twice) lands here.

**Fix:** default to a real habit for that day (`habits.getAllHabits().find(h => h.dayStart <= day)?.id`).

### 2.2 `phaseForDay()` compares LEVEL ids against DAY numbers
`src/features/ai/task-generation.service.ts:186-191`: `<=7 jee-core, <=21 l-mindset, <=63 light-execution,
else peak`. Curriculum reality (`src/data/curriculum.ts`): phase 1 = days 1–39, phase 2 = 40–63,
phase 3 = 64–81, phase 4 = 82–90. So Day 8–39 tasks get tagged `l-mindset`/`light-execution`, and
`coerceTaskEntry` (`:225`) keeps a model-supplied wrong phase as-is. Effects: `phase` unlock conditions
(`task-bank.service.ts:52-54`), Levels-screen grouping, and `baseTasksForDay`'s hardcoded
`phase: 'jee-core'` snapshot (`habit-engine/habits.ts:24-27`) all filter on phase → tasks become
invisible in the day plan.

**Fix:** `getLevelForDay(LEVELS, dayNumber)?.phase ?? 'jee-core'` (the helper already exists in
`habit-engine/context.ts:171`).

### 2.3 Day-number math is re-implemented 3 times, all ignoring rest days
Canonical helper: `contentDayForDate()` (`habit-engine/dates.ts:75`). Duplicates:
- `task-generation.service.ts:179-184` — raw epoch diff, hard-caps at **90** (not `TOTAL_DAYS`),
  no restDays → AI tasks scheduled to the wrong day for any journey with a rest day.
- `summary.service.ts:285-289` — no clamp at all, no restDays; a future-dated rollup yields
  `Day 91+`, a pre-start date yields `Day 0`/negative.
- `phase-generator.service.ts:149-153` — `new Date(state.startDateISO)` (UTC midnight) vs
  `new Date()` (local now) → the 90-day boundary moves by the TZ offset (in IST, results flip for
  ~5.5 h each day) and rest days are ignored, so post-journey mode / `finalStats` fire early.

**Fix:** one function, one call path: `contentDayForDate(todayISO(tz), state.startDateISO, state.restDays)`
+ `currentDayNumberFor(...)` for clamping; delete the three copies.

### 2.4 Journey XP / consistency / "active days" miss mock & exam completions
Planner stores those logs under separate keys: `mock:${dateISO}` / `exam:${dateISO}`
(`habit-engine/planner.ts:306-311`), and the UI reads them correctly via `task.logKey`
(`TodayScreen.tsx:823-831`). `buildJourneyOverview` instead reads only `state.taskLogs[cursor]`
(`features/chat/context-overview.ts:22`) → a completed 3-hour mock never counts toward XP,
`activeDays`, or consistency, and the same loop counts rest days as pure inactivity. The AI is fed
numbers that contradict what the user sees on the Today screen.

**Fix:** sum `taskLogs[iso]`, `taskLogs['mock:'+iso]`, `taskLogs['exam:'+iso]`, and skip days where
`isRestRaw` is true.

### 2.5 Memory rollups are keyed to the wrong week outside UTC+
`memory.service.ts:300-306`: builds a UTC-midnight Monday then formats it with `isoDate(d)` →
`isoDateInTimeZone(d, deviceTimeZone())` (`core/ports/clock.ts:44-58`). For any UTC-minus zone,
UTC-midnight Monday is still Sunday locally → **every rollup is labelled with the Sunday date** and
weeks split. The comment above the function claims "pure UTC arithmetic" — the last line reintroduces
exactly the local shift it warns about. (Date-only `createdAt` also means `weekStart()` receives
`'2026-9-3'`-shaped or full-timestamp strings from imports; `new Date(x + 'T00:00:00Z')` → Invalid
Date → `isoDate` → `toISOString()` throws → `add()` throws.)

**Fix:** `d.toISOString().slice(0, 10)` (or `dateToISO` from `dates.ts`) and guard invalid dates.

### 2.6 "Today"-based logic uses UTC instead of the app timezone (4 sites)
The app's canonical local day is `todayISO(state.timeZone)` / `isoDate()`. These bypass it:
- `social-decision-engine.ts:206` — daily proactive budget (`max 3/day`) flips at 05:30 IST, so late
  night nudges count against yesterday's budget.
- `chat-tools.service.ts:941-944` — `listTodos {date:'today'|'yesterday'}` filters by UTC date →
  "aaj ke todos" returns yesterday's list for IST early hours.
- `chat-tools.service.ts:1384` — `createBlock.createdAt` stamped with the UTC date.
- `context-overview.ts:22` loop (see 2.4).

**Fix:** route all four through `isoDate(now, tz)` / `todayISO(tz)`.

### 2.7 `syncNow()` reports success while `inFlight`/`restoring` silently no-op
`sync-coordinator.ts:186-199`: `if (this.inFlight) return;` — the Settings "Sync now" button resolves
`void` and shows "synced" even when nothing ran (a push is usually in flight at that moment). Same
`return`-silently shape in `reconcileIfStale` when `restoring`/auth-cooldown is active
(`:227-240`). No error surfaces; the UI state stays `online` with a stale `lastSyncedAt`.

**Fix:** return a status (`'busy' | 'ok' | 'offline' | 'error'`) and let the UI show it.

### 2.8 `attach()` can reject unhandled at login
`sync-coordinator.ts:150-160` returns `this.initialSync(session)`; `App.tsx:226` calls
`container.syncCoordinator.attach(session)` fire-and-forget inside `useEffect`. `initialSync` awaits
`this.sync.scopes()` (which swallows errors → `[]`, safe) but `seedServer`/`pullAll` propagate
`replaceStore`/`store.save` throws → unhandled rejection during login, no UI signal.

**Fix:** `attach(...).catch(...)` in `App.tsx`, or wrap `initialSync` in try/catch that sets scope error state.

### 2.9 Release: current version scheme vs `parseVersion` day+seq heuristic ✅verified
`parseVersion` (`src/lib/updates.ts:114-121`) assumes the last component is `DDSS`; the actual scheme
is `YYYY.MM.BUILD` (`scripts/release-version.mjs:31-32` — `2026.09.7004`). Measured:

| comparison | result | expected |
|---|---|---|
| `2026.09.7004` vs `2026.09.10000` | `1` (newer looks older) | `-1` |
| `2026.09.7004` vs `2026.09.12` | `1` | `-1` |
| `2026.09.99` vs `2026.09.100` | `1` | `-1` |

Consequence: `npm run release:date` (an advertised script producing `v$(date +%Y.%m.%d)`) yields a tag
the app considers **older** than the installed build → no in-app update, and `.github/workflows/release.yml:60-72`
computes `versionCode = 2026 09 12 00 = 20260912` vs the current `2026097004` — a **decreasing
versionCode**, which Android's downgrade protection refuses to install over the existing app.

**Fix:** pick one scheme. Either always 4-digit build and compare the third component numerically
(delete the DDSS split), or keep DDSS and validate the tag in `release-version.mjs` (`VERSION_RE` must
reject `YYYY.MM.<1 or 3 digit>`).

### 2.10 `isUpdateAvailable` is permanently true for `dev`
`src/lib/updates.ts:139-142`: `if (current === 'dev') return true`. `getEnvVersion()` returns `'dev'`
whenever `VITE_APP_VERSION` is unset — and the CI `web-build` job (`.github/workflows/ci.yml:57-70`)
never sets it. So the deployed web build always shows "update available" and offers an APK install
flow that cannot work in a browser. Also `.env.example` does not document `VITE_APP_VERSION` at all.

## 3. S3 — Robustness / platform / UX bugs

### 3.1 SSE: no final-frame flush, and the idle timer leaks when a handler throws
`src/infra/ai/http.ts:96-121`. After `done`, the leftover `buffer` is never parsed — a last event not
followed by a blank line (some gateways) is dropped → the final token of a reply disappears.
`onData` throwing (a bad `onDelta`) exits without `clearTimeout(idleTimer)` (no `try/finally`) → the
timer fires later and calls `reader.cancel()` on a finished stream. Also `requestSse` ignores
`init.retries` entirely — a mid-stream drop never reconnects, unlike `requestJson`.

### 3.2 Timeouts are never retried, despite `defaultRetries = 3`
`http.ts:203-208`: `isRetryable()` only returns true for `RETRYABLE_STATUS` codes, but `rawFetch`
maps timeouts to `HttpError(status: 0, kind:'timeout')` (`:160-165`) → `RETRYABLE_STATUS.has(0)` is
false. On mobile (the whole point of this client) a stalled request — the most common failure — gets
zero retries while a 503 gets three.

### 3.3 `looksLikeToolError` over-matches → web search silently disabled
`src/infra/ai/openai-compatible.ts:357-360` matches `/not supported|does not support|invalid argument|unknown type/i`.
Any unrelated 400 ("`temperature` not supported", "invalid `max_tokens`", "model not supported")
triggers the "endpoint rejected the search tool" retry (`:118-125`, `:186-193`) → the answer is
regenerated **without** grounding, at double latency/cost, with no indication that the search was dropped.

### 3.4 Sync restore can install the redaction sentinel as a real API key
`sync.service.ts:287` writes `live.apiKey = 'REDACTED_IN_SYNC'`. `backup.service.ts:324-336` scrubs
that sentinel on backup import, but the **sync pull path does not**: `mergeAppState`
(`sync-merge.ts:141-160`) spreads remote `live` under local, so on a fresh device (no local `live`)
the literal string becomes the Gemini Live key → opaque 403s in live calls. Same class: providers
merged from remote carry no key and no `hasKey` hint (the comment in `backup.service.ts:198-201`
promises a `has*Key: true` flag that no code ever writes).

### 3.5 Web-notification tap never deep-links, and `force` doesn't bypass `document.hidden`
- `public/sw.js:14-27` — `notificationclick` only `focus()`es the first window; no `postMessage`, no
  URL with the session id, so the "tap a web notification to open that chat" flow (implemented for
  native, `lib/notification-actions.ts`) does nothing on web. Matches the still-open M13.
- `src/lib/notifications.ts:456-472` — the web fallback fires only `if (document.hidden)`, and the
  `force` flag (used by live-call silent notifications) bypasses only the `chatTabActive` check, so a
  forced live-call notification is silently dropped on web.

### 3.6 (minor) `blob:` preview URLs are persisted into messages, backups and sync payloads
`ChatScreen.tsx:3535` mints `URL.createObjectURL`-style blob URLs for attachments and that `previewUrl`
is stored on the **persisted** `ChatAttachment` — so it reaches localStorage, backup files and the sync
payload, where it is meaningless (`blob:` is per-document; zod/`new URL()` happily accept it). Rendering
degrades gracefully — `ImageThumb` (`ChatScreen.tsx:2838-2842`) falls back to a `FileKindBadge` on error,
so sent/legacy images never show a broken frame — hence: cosmetic + dead weight. The one substantive cost
is a blob leak: URLs for *sent* attachments are revoked only in `newChat()` (`:1254`); nothing revokes
them when the 100-message trim (`chat.service.ts:320`) drops the owning message, nor on session switch.
**Fix:** keep `previewUrl` out of the persisted shape (session-scoped id → URL map) or inline small images
as data URLs so previews actually survive reload/backup/sync.

### 3.7 Browser download revokes the object URL synchronously
`src/lib/exportFile.ts:57-64` — `a.click(); a.remove(); URL.revokeObjectURL(url);`. In Firefox and
iOS Safari the download can be cancelled because the URL dies before the navigation starts. Standard
fix: revoke on the next macrotask (or after `setTimeout(..., 1000)`).

### 3.8 `ChatScreen` keeps a 300 ms poll alive forever, and the screen never unmounts
`src/screens/ChatScreen.tsx:262-280` polls `providerSigOf(listStoredProviders())` every 300 ms to
catch provider changes; `App.tsx` deliberately keeps ChatScreen mounted across all tabs (`chatVisited`).
Net effect: a permanent 300 ms wake-up for the entire app session — the same pattern the hang-fix (P3)
removed from `useAppState`. The live-config sync right below (`:283-297`) shows the correct pattern
(`container.store.subscribe`) — use it for providers too.

### 3.9 React lint warnings that are actual staleness bugs
`oxlint` reports `react-hooks(exhaustive-deps)` at `src/screens/ChatScreen.tsx:454` —
the effect resets the message window when `activeId` changes but reads `messages.length`, so switching

### 3.10 `friendlyAuthError` maps "user does not exist" to "username already taken"
`src/lib/auth.ts:120-134`: `/409|already taken|exists/i` matches the substring **"exists"** inside
"User does not exist" → a *login* with an unregistered username tells the user to use the *Register*
tab from the Login tab with a contradictory message (the 401 branch only wins if the status text is present).

### 3.11 `isConfigured()` vs `healthCheck()` disagree for local providers
`openai-compatible.ts:98-102` treats `localhost`/`127.0.0.1`/`0.0.0.0` as configured without a key,
but `healthCheck()` (`:303-307`) hard-fails with "API key missing" → Ollama/llama.cpp endpoints always

connectable host — the allowlist should use `localhost`/`127.0.0.1`/LAN ranges only.

### 3.12 Checked and cleared: Android 14+ FGS start ordering (no bug — documented so it stays that way)
`LiveCompanionForegroundService.onStartCommand` (`:40-59`) declares `FOREGROUND_SERVICE_TYPE_MICROPHONE |
MEDIA_PLAYBACK`, which on API 34+ throws `SecurityException` unless `RECORD_AUDIO` is already granted when
`startForeground()` runs. That would be a crash if `armLiveCall()` could run first — but `initialMicStream`
is a **required** prop of the overlay (`LiveCompanionOverlay.tsx:229`), so `getUserMedia` (and hence the
grant) always precedes `await armLiveCall()` (`:548`). Verified safe; keep it that way by not making that
prop optional.

### 3.13 `isLiveCallInterrupted` never clears the persisted ARMED flag
`LiveCompanionPlugin.java:162-173` only reports; `clearCallInterrupted()` runs on explicit hangup
(`:87-109`). A call that died mid-connect leaves `lifecycle = ARMED` in SharedPreferences forever →
every later launch reports `attempted: true` (a stale "you tried to call" UX) until an unrelated hangup
happens to clear it. Read-once-then-clear (or age the marker out) is the correct shape.

### 3.14 `allowBackup="true"` ships the whole app data dir (and cleartext is enabled)
`android/app/src/main/AndroidManifest.xml:38-45`: `android:allowBackup="true"` + no
`fullBackupContent`/`dataExtractionRules` → the Capacitor WebView storage — which holds
`levelup.auth.session` (JWT **and** `sk-` API key, `lib/auth.ts:26`), all provider keys, and chat —
is included in adb/cloud backup. The app deliberately redacts those keys from sync and backup exports
(`sync.service.ts:270-290`, `backup.service.ts:190-215`), so this is the remaining leak.
`android:usesCleartextTraffic="true"` (same block) additionally allows HTTP downgrade for
token-bearing requests. Also declared-but-unused Play-policy permissions: `RECEIVE_BOOT_COMPLETED`
is used by the plugin, but `FOREGROUND_SERVICE_PHONE_CALL`, `USE_EXACT_ALARM` (restricted to
alarm/calendar apps) and `SCHEDULE_EXACT_ALARM` have no matching code path — a store-review risk.
